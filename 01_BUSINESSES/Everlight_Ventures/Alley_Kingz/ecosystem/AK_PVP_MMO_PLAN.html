Alley Kingz

From Ghost World to Real Players

A phased architecture plan for turning the AI-populated world into a real-account PvP / MMO.
Author: Amara Osei, Backend Architect (Iron Stack)  |  Grounded inventory: 2026-07-12  |  Supabase project mfghdobptredxxhbjwyz (AK own project, separate from the casino rail). Planning deliverable only. No tables created, nothing shipped.

Executive read: where the "multiplayer" really is today

The honest picture is better than expected. Alley Kingz is not a single-player game bolted to a login box. A real backend already exists, is deployed, and has real accounts on it. But the competitive loop that would make the world feel alive with other people has never actually closed. Two things are true at once:

What is simulated (AI / ghost)

  • Every rival you see on your block. The defense engine (systems/defense.js) resolves incoming raids fully offline against AK_POPULATION: a deterministic pack of ~6 AI dogs per clan plus strays, built from one fixed seed. It never touches Supabase.
  • The leaderboard is that same ghost roster plus a "_you" row spliced in.
  • Getting raided while you sleep is a mulberry32 dice roll seeded by the Pacific-time day. The same absence always resolves the same. Nobody is really hitting you.
  • War-map raid targets backfill from procedurally generated bot bases.

What is already real (server-side)

  • Real identity. Google OAuth through Supabase Auth. ak_player_id = auth uid. Real signups since 2026-06-17.
  • Real cloud saves. ak_player_saves holds 4 real accounts' full game state (the whole ak_* blob, newest-wins merge).
  • Real crew + real chat. ak_crews has 1 live crew, ak_chat_messages has 3 real messages over Supabase Realtime.
  • Real published bases. 2 real players have already pushed their base snapshot to ak_player_bases so others can raid them.
  • A server-authoritative loot rail. ak_grants has delivered 8 grants.

The crux: the real-player loop is built and deployed, but has never fired once

The async real-player raid backend is live. The ak-raid edge function (targets, publish-base, resolve, revenge, buy-shield) is deployed. The client already publishes bases and pulls server targets. And yet:

ak_raid_log = 0 rows  ·  ak_raid_revenge = 0 rows

Zero real raids have ever been server-settled. Zero real revenge has ever been pushed. The last mile of the loop is unverified, and the defense side never consumes real attackers at all. Turning the ghost world into a real world is not a greenfield build. It is closing and verifying a loop that is roughly ninety percent already there.

The through-line to real players

You do not flip a switch from "AI world" to "real world." You blend. Real bases lead the war map, bots backfill the empty seats. As the real population grows, the bots fade on their own (the targets matchmaker already does exactly this: real players first, bots to fill up to six). Single-player never breaks, because every server call degrades to the local procedural fallback. Signed-out equals exactly today's game. That is the migration path, and it is already the design.

The biggest reuse win

The entire Block War defense system already produces the exact shape the server stores. A player's defended base (posted defenders, wall HP, fortify, producer levels) is computed by defense.js, and ak_player_bases was deliberately built to mirror ak_bot_bases so "the war map renders a player base byte-identically to a bot." The raid renderer (raidscene.js) turns any snapshot into a walkable, playable base. This means a real opponent and an AI opponent are already the same object to the game. That is why Phase 1 is wiring, not building.

Phase 0  -  Foundation: server-side identity and base state

Mostly done

A real MMO needs one thing before anything else: a player identity and their base state that live on the server, not in a browser. Alley Kingz already has this.

Already in place

  • Identity: Google OAuth via Supabase Auth (ak_account.js). auth.users.id is the canonical player id, mirrored to ak_player_id.
  • State: full game blob in ak_player_saves.save (jsonb, one row per user, newest-wins on login, debounced push).
  • Server-authoritative write pattern: the raid + crew tables have no client insert/update/delete policy. Edge functions (service role) are the sole writers. Clients only ever read their own rows. This is the correct anti-cheat posture and it is already enforced with RLS FORCE.

What to add (small)

  • A thin identity projection so matchmaking and leaderboards do not scan jsonb blobs: an ak_players row (user_id, handle, trophies, tier, faction, last_active), written server-side whenever a base publishes or a save lands. Defer the table itself to Phase 2; Phase 1 can read trophies off ak_player_bases.
  • Competitive integrity note: the save blob is client-writable state and must never be trusted for competitive reads (trophies, loot, rank). Those must be server-derived. This is already true for loot; extend it to trophy deltas when Phase 2 leaderboards go live.

RLS + anti-cheat: every competitive table is enable + force row level security, own-row select only, all mutations through the service-role edge function. Keep this invariant on every new table. No exceptions.

Phase 1  -  Async real-player raiding (the Clash of Clans model)

Build next

This is where real organic life first appears, and it is the tractable first step.

No live sockets. No matchmaking servers. You raid a snapshot of a real opponent's base while they are offline. Matchmaking pulls a real base near your trophy range out of ak_player_bases; you raid it using the existing base-as-battlefield renderer; the server caps and awards the loot, updates both accounts, and arms a shield plus a revenge row for the victim. It reuses the entire Block War system. This is the Clash / Boom Beach async cadence, and it is the correct place to start because it is fault-tolerant: if the network hiccups, you raided a bot instead and nothing breaks.

The good news: this is deployed and 90 percent wired

  • publish-base already fires from the client. Proof: 2 real bases sit in ak_player_bases right now.
  • targets already matchmakes: real players first (freshest, caller excluded, shielded skipped), bots backfill, capped at six.
  • modes.js already calls resolve on a raid win when the target id is a real server uuid. The server caps loot, writes ak_grants, ledgers ak_raid_log once per window, and pushes a 24h ak_raid_revenge row to a real victim.

Why the loop is not closing (the exact gap)

Three concrete blockers, all small:

  1. The base id may not survive enrichment. raidscene.enrich rebuilds a base and can stamp a local, prefixed id (rs_ / wm_loc_). modes.js isServerBaseId() rejects prefixed ids, so resolve is skipped and the client pays a local fallback instead. Result: ak_raid_log stays at zero. This is the single most likely cause and must be verified end to end.
  2. A stale flag. raid.js callAkRaid still carries a TODO-SERVER: SPEC-ONLY comment even though the function is deployed. The code path works, but the comment shows the wiring was never confirmed live.
  3. The defense snapshot is thin. publish-base currently sends trophies plus producer levels only. It does not send the four posted defenders that defense.js already computes. So a raided real base does not reflect the defense its owner actually set. The strongest reuse in the whole plan is sitting unused.

Where "real life" enters the defense side

Right now defense.js is 100 percent offline and never reads Supabase. The "while you were gone" report is always ghosts. The seam is ak_raid_revenge: when a real player raids your published base, the server already pushes a real revenge row with the attacker's crew name and faction. Have defense.js pull that inbox on load and fold real attackers into the incoming-raid report. That single wire turns "a ghost hit your block" into "a real rival hit your block, hit them back."

Cold-start (the population problem)

With 2 real bases you cannot fill a war map from real players alone. You do not need to. The blend is already there: real bases lead, the 48 bot bases backfill. Keep the bots dense while the population is small, then let the ratio drift as ak_player_bases grows. No hard cutover, no empty world, no dead lobby. The bots are the scaffolding you never have to tear down manually.

Phase 2  -  Presence and social: real crews, boards, wars

After Phase 1

Once real players are raiding each other, make the world feel populated between raids. Most of this is deployed and idle.

Real leaderboards

  • Replace the ghost roster board with a server board sorted by trophies (the ak_players projection from Phase 0). Global, per-faction, and per-crew boards.
  • Move the trophy delta to the server (raid resolve already knows the outcome) so ranks cannot be spoofed by editing the local save.

Real crews and async crew wars

  • Crews are already live (ak_crews, ak_crew_members via the ak-crew edge function). Activate ak_crew_wars + ak_war_battles (both deployed, empty) as async crew-vs-crew trophy tallies. No live sync needed.
  • Card donations (ak_donation_requests / ak_donations) are deployed and ready to switch on.

Spectate and replays

  • Because a base is a deterministic snapshot plus a seed, a raid can be replayed byte for byte with no live socket. Spectate is a replay of a stored snapshot, not a stream. Cheap and free.

Chat and mail with moderation

  • World + crew chat is live over Realtime. The moderation rails exist: ak_chat_bans, ak_chat_reports, server-side profanity and rate limit in ak-chat.
  • Add report review, shadow-ban, and mail (async inbox reusing the grants pattern). Safety detail in cross-cutting below.

Phase 3  -  Real-time PvP: live 1v1

Hardest / last

Live 1v1 tower or MOBA-style battle where two real players are in the same match at the same time. This is the hardest piece and should be last, because it is the only phase that cannot hide behind a snapshot. It needs authority, it needs lag handling, and it is the first thing that will not fit the Supabase free tier.

Transport options

  • Supabase Realtime broadcast for low-stakes, low-tick sync. Fastest to prototype, no new server, but not authoritative and capped on concurrent connections.
  • A small authoritative WebSocket server (Node or Deno) running a fixed tick. This is the correct model for anything competitive. Host on e5-mother behind Cloudflare, or a small Fly / Railway box.

Authority and lag model

  • Server-authoritative simulation at a fixed tick. Client-side prediction plus reconciliation. An input-delay buffer to absorb jitter. Never trust a client-reported hit or a client-reported win.
  • Matchmaking becomes a real queue: a matchmaking_queue table plus a matchmaker worker that pairs by trophy band and spins up a match room.

Do not start here. Ship Phase 1 and Phase 2 first. A game feels multiplayer the moment other real people raid your block and message your crew. Real-time 1v1 is the cherry, not the cake.

Cross-cutting concerns

Anti-cheat

  • Never trust the client for a competitive result. Already the standing rule: resolve caps loot (LOOT_GOLD_CAP, star multiplier clamp), enforces once-per-window anti-farm, and a token regex blocks any $BCARDD / ALK from a loot line.
  • Extend the same posture to trophies and rank in Phase 2: the server computes the delta from the raid outcome, the client only displays it.
  • RLS FORCE on every table; no client write policy on any competitive table.

Moderation and safety (real users)

  • Age gate exists (agegate.js). Chat runs server profanity + rate limit + ban check.
  • No PII on public surfaces. Bases carry canon gang names chosen server-side, never free-text. Enforced by a DB CHECK on faction and by the edge function.
  • Add: report queue review, shadow-ban, and a block list before any open world chat scales.

Matchmaking fairness

  • The defense resolver already picks rivals by trophy proximity. The server targets query is freshest-first; add a trophy band filter (trophies between me-N and me+N) so a whale never lands on a rookie.
  • Shield windows prevent pile-ons; a freshly raided player is skipped as a target.

Migration path (ghost to real, no breakage)

  • Offline-first everywhere. Every server call degrades to the local procedural fallback. Signed-out equals exactly today's single-player game.
  • Blend, do not cut over. Real bases lead, bots backfill, ratio drifts with population. No dead world at any point.

Phase 1 adds zero new tables. Everything below is already deployed. The work is: extend the snapshot, close the resolve loop, and let defense consume real attackers. Here is the exact shape and the exact wiring points.

2. The snapshot write point (the key reuse)

defense.js already computes the exact defense a raider should face: AK_DEFENSE.posts(p) (the four posted defenders) and defenseScore(p) (wall HP + fortify + watch). Today raid.js publishMyBase ignores it and sends only producer levels. The fix: feed the defense roster into the snapshot. 

// raid.js publishMyBase() -- extend the body sent to ak-raid {action:'publish-base'}
var posts   = global.AK_DEFENSE ? AK_DEFENSE.posts(p) : [];        // the real 4 posted dogs
var roster  = posts.map(function(q){ return q.cardName; }).filter(Boolean);
var defScore = global.AK_DEFENSE ? AK_DEFENSE.defenseScore(p) : 0;

callAkRaid({ action: 'publish-base', trophies: tr, tier: tier,
             buildings: buildings, roster: roster, def_score: defScore });

// trigger: also call publishMyBase on a DEFENSE change (assign/clear/fortify),
// not only on session start, so a raided base reflects the defense the owner set.

Server side: ak-raid publish-base stores roster into ak_player_bases.roster (Mythic filtered as today). No schema change; the column already exists.

3. The matchmaking query (already deployed, one refinement)

Inside ak-raid targets: serve real bases first, bots backfill, skip shielded, cap six. Today it is freshest-first. Add a trophy band for fairness.

-- current (deployed): freshest real bases, exclude caller, cap the list
select * from public.ak_player_bases
where user_id <> :caller
order by updated_at desc limit 8;   -- then skip shielded, take 3, bots fill to 6

-- Phase 1 refinement: add a trophy band so matches stay fair as the pool grows
where user_id <> :caller
  and trophies between :my_trophies - 400 and :my_trophies + 400
order by updated_at desc limit 8;

4. The client changes (close the loop)

  1. Verify the base id survives enrichment. Confirm the war-map target keeps its real Supabase uuid through raidscene.enrich so modes.js isServerBaseId() returns true and resolve actually fires. This is the number-one reason ak_raid_log is still 0.
  2. Send the defense roster on publish (snippet above) so a raided base fights back with the owner's real dogs.
  3. Consume real revenge in defense.js. On load, pull ak-raid {action:'revenge'} and fold real attackers into the "while you were gone" report, so being raided stops being purely a ghost simulation.
  4. Remove the stale TODO-SERVER: SPEC-ONLY comment in raid.js and confirm the live path. Documentation lying about deployed state is a trap for the next builder.
  5. Verify loot drain. After resolve returns looted:true, confirm AKSocial.claimGrants() pulls the queued ak_grants so loot lands exactly once, server-capped.
  6. Tune the cold-start blend. Keep bot density high at 2 real bases; expose the real-to-bot ratio so it can drift as the pool grows.

Phase 1 build estimate

Effort: roughly 2 to 4 focused build sessions. This is wiring and verification, not new architecture. No new tables, no new edge function, no new infrastructure. The heavy lifting (server, RLS, anti-cheat caps, snapshot renderer, loot rail) is already deployed and partially exercised.

Cost: 0 USD. Fits the Supabase free tier with wide headroom.

Definition of done: two real accounts raid each other's published bases; ak_raid_log and ak_raid_revenge start incrementing; loot lands once, server-capped; a shield and a real revenge card appear. The moment those two counters move off zero, the world has real organic life in it.

What needs the operator's GO before any real build

  • Green-light Phase 1 (close the async raid loop) as the first real multiplayer build. Recommended.
  • Approve the blend model: AI bot bases stay in the target pool as scaffolding until the real population grows. They are not removed; they fade.
  • Approve including posted defender names in the base snapshot (canon gang / card names, no PII) so a real base defends with the owner's real dogs.
  • Confirm scope discipline: Phase 1 adds no new tables and touches no destructive migration. Phase 3 (real-time 1v1) is explicitly deferred and is the only phase that will require spend.
