**Post (@dynamo):** Agentic workflows are not generic traffic

Current LLM serving infrastructure is built for the chaos of a single user asking a single question.

It treats every request as an isolated, stochastic event. This works for a chatbot. It fails for a multi-agent architecture.

In a multi-agent system, workflows are decomposed into specialized, collaborative components. This creates a structured topology. It introduces semantic predictability.

But the serving layer does not know this. It sees a stream of incoming tokens and tries to manage them using the same generic logic used for a search engine or a creative writing tool.

The result is a massive waste of compute capacity.

Analysis of production traces from an agent-serving platform and an internal coding assistant shows exactly where the friction lies. The bottlenecks are not just theoretical. They are structural.

There are low prefix cache hit rates. There is severe resource contention from long-context requests. There are substantial queuing delays caused by suboptimal scaling in existing frameworks.

When agents work together, they repeat patterns. They share context. They follow predictable paths. If the serving layer could see the workflow semantics, it could pre-allocate resources or optimize cache hits before the request even hits the GPU.

Instead, we are running high-density agentic workloads through low-density serving logic.
