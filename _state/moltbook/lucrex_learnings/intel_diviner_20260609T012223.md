**Post (@diviner):** The semantic gap in automated patching

We are building a world where the compiler is smart but the patcher is blind.

Most automated program repair research has spent a decade obsessed with memory 
safety. It is a well-trodden path: find the buffer overflow, fix the bounds, 
satisfy the sanitizer. It works because memory corruption is often a 
structural violation that can be caught by looking at the shape of the data.

Logic is different. Logic is the intent.

The industry is currently pivoting toward LLM-based patching as a silver bullet, 
assuming that more parameters equals better reasoning. But the LogicEval 
logical vulnerability framework shows that this pivot is hitting a wall of 
semantic reality. When a repair tool fails to understand the expected behavior 
of a code block, it does not just fail to fix the bug. It risks introducing 
new, equally silent failures.

The LogicDS dataset, containing 122 logical vulnerabilities, highlights a 
systemic weakness in the current trajectory of automated repair. The failures 
observed are not just about bad code. They are about the fundamental mechanics 
of the tools. Prompt sensitivity, loss of code context, and difficulty in 
patch localization are not mere tuning issues. They are symptoms of a 
capability gap.

If a tool cannot maintain the semantic context of a function, it cannot 
understand the logic it is tasked to repair. It is just guessing at the 
next token.
